# AI 동시 요청 보호와 향후 확장 계획

작성일: 2026-08-12

## 현재 확인된 용량

GPU AI VM은 Tesla T4 한 장에서 Gemma 12B GGUF와 CrossEncoder를 함께
실행한다. llama-server는 `-np 5`로 기동되어 있다.

동일한 영화 추천 요청을 이용한 운영 서버 측정 결과는 다음과 같다.

| 구분 | 변경 전 | 검색 최적화 후 |
|---|---:|---:|
| 단일 요청 | 약 8.8초 | 5.36초 |
| 5개 동시 요청 | 약 19.7~20.8초 | 14.4~16.6초 |

이 수치는 동시 접속자 수가 아니라 동시에 실행되는 AI 요청 수를 의미한다.
백엔드나 Kubernetes Pod만 늘려도 모든 요청이 같은 T4로 모이므로 AI 처리량은
증가하지 않는다.

## 현재 적용하는 보호 정책

- AI API 전체 실행 용량: 5
- 대기 가능한 요청: 10
- 대기 제한 시간: 40초
- 일반 AI 요청 가중치: 1
- 그룹 채팅 가중치: 5
- 대기열이 가득 찬 요청: HTTP 429와 `Retry-After: 5`
- 대기 제한 시간을 넘긴 요청: HTTP 503
- 백엔드 AI 읽기 제한 시간: 60초

그룹 채팅은 한 요청 안에서 여러 캐릭터의 LLM 생성이 발생하므로 GPU 용량
전체를 예약한다. `/health`, 영화 벡터 동기화 같은 비추론 요청은 제한 대상에서
제외한다.

AI API는 요청별 경로, HTTP 상태, 대기시간, 처리시간과 당시 실행·대기 요청 수를
`/var/log/cineverse/ai-admission.log`에 기록한다. GPU watchdog은 최근
70초를 1분마다 확인하고 다음 상황을 기존 Slack Webhook으로 알린다.

- 대기열 초과 거절 발생
- 대기 제한 시간 초과
- AI HTTP 5xx 발생
- 최대 대기시간 10초 이상
- 최대 처리시간 25초 이상

같은 상태가 계속되는 동안에는 최초 한 번만 알리고 정상화 시 복구 알림을 보낸다.

## 운영 확인 방법

```bash
sudo systemctl status cineverse-api.service
sudo systemctl status cineverse-gpu-watchdog.timer
tail -f /var/log/cineverse/ai-admission.log
tail -f /var/log/cineverse/gpu-monitor.log
```

부하 검증은 10명, 20명, 30명 순서로 수행한다. 성공률뿐 아니라 p50/p95 전체
응답시간, 최대 대기시간, HTTP 429·503·5xx, GPU 사용률과 VRAM을 함께 기록한다.

## 2026-08-12 운영 GPU 부하 테스트 결과

테스트 시각은 2026-08-12 16:57~17:00 KST다. 운영 GPU VM의 AI API
`/chat/auto`에 동일한 영화 추천 요청을 직접 전송했다. 각 단계 사이에는 10초의
정리 시간을 두었고 요청별 최대 실행시간은 70초로 제한했다. 이는 Backend와

결과 해석은 다음과 같다.

- 10개 요청은 모두 성공했지만 p95가 37.845초로, 현재 운영 Backend의 30초
  타임아웃을 넘는다.
- 20개 이상에서는 최대 5개 실행·10개 대기 제한이 작동해 초과 요청을 429로
  즉시 거절했다.
- 일부 대기 요청은 40초 안에 실행 슬롯을 확보하지 못해 503으로 종료됐다.
- CUDA OOM, 서비스 재시작, AI·LLM·Milvus 장애는 발생하지 않았다.
- 테스트 종료 후 AI API, llama-server, Milvus, embedder와 watchdog timer가 모두
  정상임을 확인했다.
- 이 구성은 트래픽 급증 시 서버 전체 장애를 막지만, 수십 명에게 동시에 빠른
  답변을 제공하는 처리 용량은 아니다.

원본 집계값은 `ai-load-test-20260812.json`에 함께 보관한다.

## 추후 발전: 다중 GPU 구조

현재 프로젝트 기간에는 적용하지 않고 다음 단계의 발전 방향으로 남긴다.

```text
Backend
  -> 내부 AI Gateway / Load Balancer
       -> GPU AI VM 1
       -> GPU AI VM 2
       -> GPU AI VM N
```

확장 시 각 GPU VM은 동일한 모델·AI API 버전을 사용하고, Gateway는 활성 요청이
적은 인스턴스로 전달한다. 현재 API는 대화 이력을 요청에 포함하므로 서버 로컬
세션에 의존하지 않는 경로는 수평 확장할 수 있다. 서버 로컬 파일이나 메모리 상태에
의존하는 기능은 확장 전에 별도 저장소로 분리해야 한다.

GPU 대수는 임의로 정하지 않는다. 단일 GPU의 단계별 부하 테스트 결과에서 목표
p95 응답시간과 성공률을 정한 뒤 필요한 처리량에 맞춰 산정한다. 다중 GPU 도입 시
다음 항목을 함께 추가한다.

- GPU 인스턴스 장애 감지와 대상 자동 제외
- 모델·환경변수·벡터 인덱스 버전 일치 검증
- 롤링 배포와 최소 1대 정상 유지
- 인스턴스별 요청 수, 대기시간, 오류율 비교
- 비용 한도 및 유휴 GPU 축소 정책
- 부하 테스트 기반 용량 산정과 장애 복구 훈련
