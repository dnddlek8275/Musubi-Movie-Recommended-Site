# 일반 채팅 불완전·의미 불명확 입력 복구

기준일: 2026-08-10

## 목적

일반 채팅에서 미완성 입력이나 감정 반응만 전송됐을 때 의도를 지어내 답하지 않고,
사용자가 자연스럽게 대화를 이어갈 수 있는 짧은 응답을 반환한다.

일반 채팅의 AI 이름은 `무무`로 통일한다. 일반 LLM 응답과 GPU를 호출하지 않는
입력 복구 응답 모두 응답 발화자 및 저장 메시지의 `character`를 `무무`로 기록한다.

## 처리 기준

| 입력 예시 | 분류 | 응답 방향 | 감정 |
|---|---|---|---|
| `ㅇ`, `ㅏ`, `ㄱ.`, `ㄴㄹㅇㄹㄴ` | 불완전하거나 의미 불명확한 자모 | 뜻을 만들지 않고 입력을 확인 | `thinking` |
| `.`, `!` | 문장부호만 입력 | 입력 중이었는지 부드럽게 확인 | `thinking` |
| `...`, `…` | 말 고르기 | 천천히 이야기해도 된다고 안내 | `thinking` |
| `?` | 질문 신호 | 궁금한 점을 이어서 말하도록 안내 | `thinking` |
| `ㅋㅋ`, `ㅎㅎ` | 웃음 반응 | 재미있는 일을 물어봄 | `joy` |
| `ㅠㅠ`, `ㅜㅜ`, `😢`, `😭`, `🥲` | 속상함 반응 | 괜찮다면 천천히 말하도록 안내 | `sorry` |

`왜`, `응`, `네`, 일반 문장과 단독 이모지는 의미 있는 메시지로 보고 기존 대화
흐름에 전달한다. `ㅇㅇ`, `ㄴㄴ`, `ㄱㄱ`, `ㅎㅇ` 같은 일반적인 초성 채팅과
`ㄴㄴ 그거 말고` 같은 문맥형 표현도 차단하지 않고 이전 대화 기록과 함께 AI로
전달한다.

AI 프롬프트는 전달받은 짧은 입력을 이전 대화와 함께 판단한다. 문맥으로 의미를
특정하기 어렵거나 확신이 낮으면 뜻을 만들어내지 않고 짧고 자연스럽게 다시 묻는다.
프롬프트만으로 이 규칙을 보장할 수 없으므로 AI API에도 같은 고확신 자모 난타
방어를 두어 Backend를 우회한 요청에서도 의미를 지어내지 않게 한다.
Backend와 AI API는 자모 난타, 문장부호, 말줄임표, 질문 신호, 웃음, 속상함을
같은 `kind`로 분류한다. 분류는 같게 유지하지만 응답 문구는 일반 AI와 캐릭터
대화의 분위기에 맞게 달라질 수 있다.

## 처리 위치

- 로그인 일반 채팅: PostgreSQL에 사용자 입력과 복구 응답을 저장하되 GPU AI를 호출하지 않는다.
- 비회원 일반 채팅: GPU AI를 호출하지 않고 즉시 응답하며 일일 이용 횟수를 차감하지 않는다.
- 캐릭터 1:1 비스트리밍·스트리밍 및 그룹 채팅: 순수 자모 난타는 AI API에서
  LLM 호출 전에 재질문하며, 그룹에서는 첫 캐릭터만 답하고 추가 반응 라운드는 만들지 않는다.
- AI API 직접 호출: 순수 자모 난타는 LLM 호출 전에 재질문하고, 허용 약어와 문맥형
  표현은 기존 대화 기록과 함께 LLM에 전달한다.
- 입력 복구 응답의 intent는 일반 캐릭터 대화와 구분되는 `input_recovery`를 사용한다.
- 대화 기록이 없는 `ㅇㅇ`, `ㄴㄴ`, `ㄱㄱ`, `ㅎㅇ`는 정해진 짧은 문장으로 답한다.
  이전 대화가 있으면 `ㅎㅇ`를 제외한 약어는 문맥과 함께 LLM이 판단한다.
- Backend와 AI의 허용 약어 목록은 단위 테스트에서 동일 여부를 검사한다.
- Backend와 AI의 대표 입력별 복구 `kind`도 단위 테스트에서 동일 여부를 검사한다.
- 입력 복구 응답은 기존 채팅 타이핑 `...` UI가 보이도록 약 0.6초 후 반환한다.
  일반 AI·영화 추천 응답에는 이 지연을 적용하지 않는다.
- 그룹·캐릭터 스트리밍은 복구 응답의 `input_recovery` 메타데이터를 프론트가
  확인하여 기존 점 3개 UI를 요청 시작부터 최소 600ms 유지한다. 정상 응답과 실제
  AI 생성 시간에는 추가 지연을 적용하지 않는다.

## 자연스러운 속도 제어 방향

복구 요청을 비회원 일일 AI 이용 횟수에 포함하거나 정상 사용 중 바로 오류를
보여주는 방식은 사용하지 않는다. 인프라 구축 후 다음처럼 단계적으로 적용한다.

1. 프론트는 현재처럼 응답 처리 중 중복 전송을 막는다.
2. Backend는 회원 ID 또는 비회원 식별 키 기준으로 짧은 구간의 복구 요청량을 센다.
3. 짧은 순간의 초과는 제한 오류 대신 아주 짧은 내부 대기와 동일 요청 병합으로
   흡수하고, 로그인 사용자의 동일 복구 메시지는 연속해서 DB에 중복 저장하지 않는다.
4. 자동화 공격처럼 대기만으로 감당할 수 없는 극단적인 요청에만 `Retry-After`가
   포함된 제한 응답을 사용하고, 프론트는 가능한 범위에서 자동 재시도하며 기존
   로딩 UI를 유지한다.
5. 다중 Backend Pod 환경에서는 Pod별 메모리 카운터가 서로 달라지므로, 실제 임계값과
   공유 저장 방식은 인프라 모니터링 결과를 확인한 뒤 결정한다.

이 방식의 목표는 정상 사용자의 대화는 자연스럽게 이어가면서, 중복 DB 기록과
복구 엔드포인트 폭주만 내부적으로 줄이는 것이다. 현재는 설계만 기록하며 임계값은
근거가 생기기 전 임의로 정하지 않는다.
