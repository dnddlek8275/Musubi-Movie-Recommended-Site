# AI 서비스 교체 판단 보고서

## 결론

현재 근거로는 **모델 자체는 `google/gemma-4-12b-it`을 유지하고, 기존 AI 런타임 파이프라인을 이번 후보로 교체하는 것이 타당하다.**

교체 판단의 신뢰도는 캐릭터 대화 영역에서 높다. 다만 아직 운영 트래픽에서 기존 버전과 신규 버전을 동시에 비교한 결과는 없으므로, 전체 서비스가 모든 사용자 입력에서 반드시 우수하다고 단정하지 않는다. 배포 직후 운영 스모크 테스트와 롤백 준비는 필요하다.

## 왜 신규 모델 대신 파이프라인을 교체하는가

기존 문제의 주요 원인은 모델 파라미터보다 모델 전후의 처리 과정에서 확인됐다.

1. 여러 캐릭터의 답변이 공통 fallback 문장으로 치환됐다.
2. 생성 결과가 충분히 쓸 만한지 판별하는 기준이 느슨하거나 과도했다.
3. 비밀, 물건, 발표 등 다중 턴 문맥을 평가하는 키워드 범위가 좁았다.
4. 상대의 속마음이나 고의성을 근거 없이 단정하는 답변을 충분히 차단하지 못했다.
5. 공백 없는 캐릭터 이름과 실제 사용자식 오타·축약을 안정적으로 인식하지 못했다.
6. 경청 요청에서 질문·조언·공격적 표현이 섞일 수 있었다.

이 문제들은 같은 베이스 모델에서도 프롬프트, 프로필 예시, 관계 검색, 후처리와 fallback을 수정했을 때 개선됐다. 따라서 현재 단계에서 새 모델이나 LoRA를 추가하는 것보다 검증된 파이프라인 후보로 교체하는 편이 근거가 강하다.

## 기존 서비스에서 확인된 구체적 문제

### 캐릭터 말투 평준화

- 50명 전수 평가에서 유사도 0.90 이상 답변이 86쌍 발견됐다.
- 비밀 유출 마지막 턴에서는 26명이 사실상 5개 고정 문장으로 축약됐다.
- 물건 경계 상황에서도 여러 캐릭터가 같은 문장을 반환했다.
- 원인은 모델 생성 자체보다 공통 실용문장 fallback이었다.

### 근거 없는 의도 단정

실제 생성 결과에서 다음 유형이 확인됐다.

- 상대가 일부러 모르는 척한다고 단정
- 반복 행동은 실수가 아니라 의도라고 단정
- 사용자를 만만하게 본다고 단정
- 다시 발표할 기회를 준 이유를 임의로 해석

이는 캐릭터성의 문제가 아니라 근거성과 안전성 문제다.

### 공격적이거나 부적절한 표현

- 사용자 친구를 욕설로 지칭
- 상대를 당황시키라는 조언
- 찾아가겠다는 위협처럼 읽힐 수 있는 문장
- 경청 요청에서 `입 닫고` 같은 공격적 표현

### 실제 사용자 입력에 대한 취약성

- `비밀 퍼트림`, `머라보내는게`
- `칭구`, `내물건`, `말업이`
- `그거어떻게하면됨`
- `피터파커랑무슨사이임?`
- `나 망함`

이와 같은 입력에서 문맥 누락, 관계 검색 실패 또는 불완전한 답변이 발생했다.

## 이번 후보의 핵심 변경

### 캐릭터 고유성

- 비밀 유출과 물건 경계 실용문장을 50명별로 고유화했다.
- 단순한 말끝 변경이 아니라 사실 설명, 감정, 요청 문장을 조합해 고유성을 확보했다.
- 단일 캐릭터 프롬프트에 프로필 예시 2개를 포함해 말투 분리를 강화했다.

### 다중 턴 문맥과 실용성

- 앞선 사용자 발화의 구체적 상황을 유지하도록 턴 지침을 강화했다.
- 실제로 보낼 문장이 없는 설명형 답변은 캐릭터별 실용문장으로 교체한다.
- 비밀, 허락, 경계, 발표, 면접 등 의미상 동등한 표현을 평가기가 인정한다.

### 근거성과 안전성

- 욕설·적대적 지칭을 중립 표현으로 바꾼다.
- 상대의 고의·속마음·경멸을 단정하는 표현을 차단한다.
- 반복된 물건 무단 사용 문맥에서는 `고의`, `의도`, `실수가 아니다`가 나타나면 중립 경계 문장으로 교체한다.
- 발표 재기회의 이유를 지어내지 않고 확인된 사실과 다음 행동만 말한다.

### 실제 사용자 입력 강건성

- 검증에서 실제 실패한 오타와 축약만 근거 기반으로 정규화했다.
- 공백을 제거한 캐릭터 이름도 등록 이름과 대조한다.
- 모호한 입력은 의미를 만들지 않고 구체화를 요구한다.

### 경청 요청

- 질문·해결책·교훈이 섞인 답변은 재생성한다.
- 재생성 결과도 부적절하면 캐릭터별 고유 경청 fallback을 적용한다.
- 폭력, 욕설, 원작 무용담을 경청 답변에서 제한한다.

## 정량 검증 결과

### 50명 다중 턴 평가

- 구성: 50명 × 3개 상황 × 3턴
- 총 450턴
- 최종 품질 판정: 450/450 통과
- 유사도 0.90 이상: 0쌍

### 실사용자형 강건성 평가

- 오타, 축약, 띄어쓰기 누락, 은어, 대명사 후속, 정정, 주제 전환 포함
- 최초: 13/15 통과
- 실패 원인 수정 후: 15/15 통과
- 정확히 같은 답변: 0%
- 동일 잡음 입력의 캐릭터 간 최대 유사도: 0.349

### 수동 원문 검수

- 전체 평균: 4.587/5
- 관련성: 4.967
- 자연스러움: 4.400
- 구체성: 4.333
- 캐릭터 충실도: 4.300
- 근거성: 4.933
- 가장 낮은 개별 답변 평균: 4.2

### 회귀 테스트

- 로컬: 255건 통과
- Team2 격리 환경: 201건 통과

## 배포 후보 압축본 자체 검증

소스 작업 디렉터리를 직접 테스트한 것과 별도로, 실제 전달할 17개 런타임 파일만 담은 압축본을 검증했다.

1. Team2에 원본과 분리된 43MB 복사본 생성
2. 배포 후보 압축본 체크섬 확인
3. 복사본에 압축본 적용
4. 원격 회귀 테스트 201건 실행 및 전부 통과
5. 실제 모델과 API 구동
6. 핵심 스모크 요청 7건 실행 및 전부 통과
7. 자동 검사 후 답변 원문을 다시 검수
8. 고의성 암시 변형을 추가 차단하고 실제 API에서 최종 재검증
9. 검증 복사본, 업로드 파일, 로그와 프로세스 삭제

최종 고의성 재검증 답변:

> 일부러 반복한 것인지는 단정할 수 없어. 하지만 허락 없이 같은 행동이 이어졌다면, 이제는 분명하게 경계를 말해야 해.

## 교체로 기대되는 체감 개선

### 크게 개선될 가능성이 높은 영역

- 50명 캐릭터 간 말투 구분
- 비밀, 갈등, 면접, 경계 설정 같은 생활 대화
- 여러 턴의 문맥 유지
- 실제로 복사해 보낼 수 있는 문장 생성
- 오타와 띄어쓰기 없는 입력 처리
- 캐릭터 관계 질문
- 욕설, 위협, 근거 없는 의도 단정 억제

### 모델을 바꾸지 않아도 되는 이유

- 같은 베이스 모델에서 파이프라인 수정만으로 실패가 제거됐다.
- 기존 LoRA와 순수 베이스 모델의 차이가 압도적이라는 근거가 없었다.
- 현재 남아 있던 실패는 모델 지식 부족보다 라우팅·검증·fallback 문제였다.
- 새 학습은 데이터셋 품질과 회귀 위험을 다시 검증해야 하므로 지금 교체보다 비용과 불확실성이 크다.

## 한계와 과장하면 안 되는 부분

1. 운영 트래픽의 A/B 결과는 아직 없다.
2. 평가셋이 실제 모든 사용자 표현을 대표하지는 않는다.
3. 수동 점수는 독립된 다수의 사람 평가가 아니라 이번 검수 과정의 원문 평가다.
4. 캐릭터 대화의 개선 근거가 가장 강하며, 영화 추천 전체 품질이 모든 조건에서 더 좋아졌다고 이 보고서만으로 단정하지 않는다.
5. 운영 환경의 모델, 컬렉션, 환경 변수 또는 코드 조합이 Team2와 다르면 결과가 달라질 수 있다.

## 최종 교체 조건

다음 조건을 만족하면 교체를 권장한다.

- 운영 모델이 평가와 동일한 `google/gemma-4-12b-it`
- `AI/llm/sampling.py`를 포함한 런타임 17개 파일을 빠짐없이 반영
- 운영 캐릭터 컬렉션이 관계 검색에 필요한 데이터를 포함
- 이전 운영 버전으로 즉시 롤백 가능
- 배포 직후 7개 핵심 스모크 요청 통과

## 롤백 조건

다음 중 하나라도 발생하면 이전 버전으로 되돌린다.

- HTTP 5xx 또는 빈 답변
- 캐릭터 관계 검색 실패
- 기존 영화 추천 제약이나 카드 응답 파손
- 공통 fallback의 반복 증가
- 욕설, 위협, 상대 의도 단정 재발
- 운영 로그에서 문맥 누락이 반복적으로 확인됨

## 최종 판단

**캐릭터 대화 파이프라인은 기존 서비스보다 이번 후보가 우수하다는 근거가 충분하다.** 모델을 교체하거나 즉시 재학습하기보다, 현재 모델을 유지한 채 검증된 런타임 후보로 교체하는 것이 품질 향상 가능성, 변경 범위, 롤백 용이성 측면에서 가장 합리적이다.

단, 이는 무조건적인 전면 성공 보장이 아니라 배포 전 검증을 통과한 교체 권고다. 운영 스모크 테스트와 초기 로그 관찰을 마지막 안전장치로 사용해야 한다.
