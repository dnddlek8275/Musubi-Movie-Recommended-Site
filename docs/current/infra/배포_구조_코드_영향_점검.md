# 배포 구조 변경에 따른 코드 영향 점검

점검 기준 구조:

- Frontend/Backend: Kubernetes, 각각 2개 Pod
- PostgreSQL/PgBouncer: Kubernetes 외부의 별도 VM
- AI API: 별도 GPU VM
- PostgreSQL 백업: Object Storage
- 외부 요청 경로: `/`는 Frontend, `/api`는 Backend

이 문서는 저장소의 현재 코드와 Kubernetes 템플릿만을 기준으로 작성했다.
클라우드 관리자가 아직 제공하지 않은 실제 도메인, Registry, StorageClass,
사설 주소, 방화벽 정책과 자원 크기는 판정하지 않았다.

## 결론

Backend와 PostgreSQL을 같은 VM에서 분리한 것 때문에 CRUD나 ORM 코드를 전면
수정할 필요는 없다. 현재 Backend는 `DATABASE_URL`로 접속 대상을 받으며,
애플리케이션은 PgBouncer 6432, Alembic Job은 PostgreSQL 5432를 사용하도록
템플릿이 분리되어 있다.

Object Storage가 PostgreSQL `pg_dump` 백업 저장소로만 쓰이면 애플리케이션
코드 변경도 필요 없다. 반면 사용자 프로필 이미지를 Object Storage로 옮기려면
현재 로컬 파일 저장 코드를 수정해야 한다.

현재 상태에서 우선 해결해야 하는 것은 DB 분리 자체가 아니라 업로드 파일 경로,
다중 Pod 공유 저장소, 상태 검사, 마이그레이션 권한과 STT 실행 자원이다.

## 배포 전 필수 결정 및 수정

### 1. 프로필 이미지 경로가 현재 Ingress와 맞지 않음

Backend는 프로필 이미지를 `/uploads/...`로 저장하고 `request.base_url`을 붙여
`https://서비스도메인/uploads/...` 형태로 반환한다. 그러나 Ingress는
`/api`만 Backend로 보내고 `/`는 Frontend로 보낸다. 따라서 브라우저의
`/uploads/...` 요청은 Backend가 아니라 Frontend로 가게 된다.

다음 중 하나를 선택해야 한다.

1. `/uploads`를 Backend Service로 보내는 Ingress 경로를 추가하고 공유 PVC를 쓴다.
2. 외부 URL을 `/api/uploads/...`로 바꾸고 Backend로 rewrite한다.
3. 프로필 이미지를 Object Storage에 저장하고 해당 URL을 반환한다.

근거:

- `Backend/app/main.py`: `/uploads` 정적 파일 mount
- `Backend/app/api/users.py`: `request.base_url + user.profile_image`
- `infra/k8s/base/ingress.yaml`: Backend 경로가 `/api`뿐임

### 2. Backend 2개 Pod의 업로드 파일은 공유 저장소가 필요함

프로필 이미지는 Pod 로컬 파일에 기록된다. 공유 저장소가 없으면 이미지를 저장한
Pod와 조회·삭제 요청을 받은 Pod가 달라질 수 있다. 현재 Deployment는
`backend-uploads` PVC를 두 Pod에 mount하도록 작성되어 있지만, 예제 PVC는
`ReadWriteMany` StorageClass가 확정되지 않아 아직 적용할 수 없다.

관리자가 RWX StorageClass를 제공할 수 있는지 먼저 확인해야 한다. 제공할 수
없으면 프로필 이미지를 Object Storage로 변경하는 쪽이 필요하다.

추가로 현재 프로필 변경 로직은 기존 파일 삭제, 새 파일 기록, DB 반영이 하나의
원자적 작업이 아니다. 중간 실패 시 기존 파일 유실 또는 사용되지 않는 파일이
남을 수 있으므로 저장 방식이 결정된 후 함께 보완해야 한다.

근거:

- `Backend/app/services/user_service.py`: 로컬 파일 기록·삭제
- `infra/k8s/base/backend.yaml`: `/app/app/uploads` PVC mount
- `infra/k8s/uploads-pvc.example.yaml`: 미확정 RWX StorageClass

### 3. Readiness가 DB 장애를 판별하지 못함 (해결)

점검 당시 Backend의 readiness와 liveness가 모두 `/health`를 사용했다.
현재는 liveness는 `/health`를 유지하고 readiness는 DB 연결 실패 시 HTTP 503을
반환하는 `/ready`를 사용하도록 분리했다.

`/db-test`는 수동 연결 확인 API로 유지하며 Kubernetes probe에는 사용하지 않는다.

권장 분리는 다음과 같다.

- liveness: `/health`
- readiness: `/ready`

근거:

- `Backend/app/main.py`: `/health`, `/ready`, `/db-test`
- `infra/k8s/base/backend.yaml`: readiness `/ready`, liveness `/health`

### 4. 운영 마이그레이션 계정 권한을 확인해야 함

일부 Alembic migration은 `pgcrypto` extension을 생성한다. 별도 migration
계정에 해당 권한이 없으면 초기 배포가 실패한다. 관리자가 extension을 미리
설치하거나, migration 계정에 필요한 권한을 제공해야 한다.

또한 `20260703_0003_sync_external_db_schema.py`에는
`preference_type = 'character'` 데이터를 삭제하는 구문이 있다. 신규 빈 DB에는
영향이 없지만 기존 데이터를 이전할 때는 백업 후 내용을 확인해야 한다.

근거:

- `Backend/alembic/versions/25d8a2a18004_add_refresh_tokens_table.py`
- `Backend/alembic/versions/20260714_0009_create_password_reset_tokens.py`
- `Backend/alembic/versions/20260714_0010_create_email_verification_codes.py`
- `Backend/alembic/versions/20260703_0003_sync_external_db_schema.py`

### 5. STT 모델과 Pod 자원을 확정해야 함

음성 인식은 Backend Pod 안에서 CPU용 faster-whisper `small` 모델을 처음 요청할
때 불러오며 프로세스별로 캐시한다. Docker image에는 모델이 포함되어 있지 않다.
따라서 각 Pod가 최초 요청 시 모델을 받을 수 있는 인터넷 경로와 디스크가
필요하고, 두 Pod가 각각 모델 메모리와 CPU를 사용한다.

현재 CPU·메모리 requests/limits가 없으므로 실제 자원 측정 전에는 STT가 안정적으로
동작한다고 판정할 수 없다. 운영에서 STT를 사용할 경우 모델을 image에 포함할지,
공유 cache를 사용할지, 별도 서비스로 분리할지와 Pod 자원을 결정해야 한다.

근거:

- `Backend/app/services/speech_to_text_service.py`
- `Backend/Dockerfile`
- `infra/k8s/base/backend.yaml`

## 코드 기능 오류

### Frontend 추천 영화 API 오타 (해결)

Frontend 호출 경로를 Backend 실제 경로인
`/user/chatai-recommended-movies`로 수정했다.

근거:

- `Frontend/src/api.js`
- `Backend/app/api/users.py`

### AI 상태 검사가 비정상 HTTP 응답도 성공으로 표시함 (해결)

`/ai-health`가 AI 서버의 4xx·5xx 응답을 검사하고, timeout은 504, 연결 실패와
비정상 상태 응답은 502로 반환하도록 수정했다.

근거: `Backend/app/main.py`

### AI 채팅 오류가 HTTP 200으로 변환되는 문제 (AI 채팅 해결)

AI 채팅 API가 `HTTPException`을 그대로 다시 발생시키도록 수정해 timeout 504,
연결·upstream 실패 502를 보존한다. 예상하지 못한 Backend 오류는 내부 예외
문자열을 노출하지 않고 500으로 반환한다.

`/db-test`를 포함해 이번 작업 범위 밖의 일부 API에는 오류 dictionary를 HTTP
200으로 반환하는 기존 패턴이 남아 있다. `/db-test`는 Kubernetes probe에서
제외했지만, 전체 API 상태 코드 정리는 별도 작업이 필요하다.

근거:

- `Backend/app/api/chat.py`
- `Backend/app/main.py`
- `Backend/app/ai_client/base.py`

### AI 스트리밍에 제한 시간이 없음 (해결)

캐릭터 스트리밍에 연결 5초, read 60초, write 30초, pool 5초 제한을 적용했다.
AI 연결은 `StreamingResponse`를 시작하기 전에 열어 초기 timeout은 504,
연결·upstream 실패는 502로 반환한다. HTTP 응답 시작 후 read timeout이 발생하면
SSE 오류 event를 보내고 Frontend가 이를 사용자 오류로 처리한다.

근거:

- `Backend/app/ai_client/chat.py`
- `infra/k8s/base/ingress.yaml`

## 구조와 일치하는 부분

- Backend DB 연결 대상은 환경변수이므로 별도 DB VM 주소로 교체할 수 있다.
- 애플리케이션 DB 연결은 PgBouncer transaction mode를 고려해 `NullPool`과
  prepared statement 비활성화가 적용되어 있다.
- Alembic은 별도 Job과 별도 Secret을 사용해 PostgreSQL 5432에 직접 연결하도록
  분리되어 있다.
- 임시 음성 파일은 요청 처리 후 삭제되므로 다중 Pod 공유 저장 대상이 아니다.
- AI 주소는 `AI_BASE_URL`로 외부 GPU VM을 지정할 수 있다.
- TMDB와 SMTP는 외부 서비스이므로 Worker Node의 NAT outbound와 자격증명이
  제공되면 현재 환경변수 방식으로 연결할 수 있다.
- Object Storage에 DB 백업을 올리는 작업은 PostgreSQL VM의 백업 작업이며
  Backend 애플리케이션 코드와 분리할 수 있다.
- Frontend 인증·채팅 cache의 `localStorage`는 브라우저별 상태이므로 Backend
  Pod 수와 충돌하지 않는다.

## 관리자에게 받아야 할 값

- Registry의 Frontend/Backend 실제 image 주소와 tag
- 운영 도메인, 인증서와 실제 IngressClass
- PostgreSQL/PgBouncer 사설 주소와 애플리케이션·migration 계정
- `pgcrypto` 설치 또는 생성 권한 여부
- GPU AI VM 사설 주소와 Worker Node에서의 80 포트 접근 허용
- Worker Node에서 Registry, TMDB, SMTP, STT 모델 저장소로 나가는 NAT 허용
- RWX StorageClass 제공 가능 여부와 용량
- Backend 및 STT를 고려한 CPU·메모리 requests/limits
- PostgreSQL 백업 bucket, 보존 기간, 암호화와 복구 시험 기준

## 권장 작업 순서

1. 프로필 이미지를 RWX PVC와 Object Storage 중 어디에 둘지 결정한다.
2. 결정에 맞게 `/uploads` 외부 경로와 저장 코드를 수정한다.
3. Alembic 계정 권한과 기존 DB migration 내용을 확인한다.
4. STT 실행 방식과 Backend Pod 자원을 측정·확정한다.
5. 관리자 값으로 Kubernetes template을 채운다.
6. migration Job, Backend/Frontend rollout, DB·AI·업로드 기능을 순서대로 검증한다.
