⸻

Private Subnet

● 이유
Kubernetes Worker Node, PostgreSQL VM 및 GPU AI VM이 인터넷에 직접
노출되지 않도록 Private Subnet에 배치합니다.
외부 요청은 Public ALB와 ingress-nginx를 통해서만 수신하고,
내부 서비스 간 통신은 Private IP 또는 Private DNS를 사용합니다.

● 사양
Private Subnet 1개
Kubernetes Worker Node VM 2대 배치
PostgreSQL + PgBouncer VM 1대 배치
GPU AI VM 1대 배치
모든 Private 리소스에 Public IP 미할당
인터넷 직접 접근 차단
NAT Instance를 통한 아웃바운드 통신
Security Group 기반 최소 권한 통신
Private DNS는 사용 가능 여부 확인 후 적용 권장

● 주요 통신
Public ALB → ingress-nginx
Backend Pod → PgBouncer: TCP 6432
Alembic Job → PostgreSQL: TCP 5432
Backend Pod → GPU AI FastAPI: TCP 80
Private 리소스 → Container Registry 및 외부 서비스: NAT 경유

⸻

NAT + Bastion 통합 Server

● 이유
한 대의 일반 VM이 Private Subnet의 인터넷 아웃바운드 경로와
관리자 SSH 중계 경로를 함께 담당합니다.
Private 리소스에는 Public IP를 할당하지 않고, 관리자는
NAT+Bastion VM을 경유해서만 접근합니다.

● 사양
일반 VM 1대
Public Subnet 배치
Public IP 1개
NAT 및 Bastion 역할 통합
정확한 vCPU, RAM 및 디스크 사양은 트래픽과 예산 확인 후 확정
관리자 지정 Public IP만 TCP 22 허용
SSH Key 기반 인증
Password 및 Root SSH 로그인 차단
접근 로그 및 명령 이력 보관
애플리케이션 및 데이터베이스 실행 금지
Private Subnet의 기본 경로를 NAT VM으로 설정

● 주의사항
NAT VM 장애 시 Private 리소스의 인터넷 아웃바운드와 관리 접속이
동시에 중단됩니다.
개인 SSH Key와 장기 Kubernetes 관리자 자격증명은 NAT VM에
상시 저장하지 않고, 관리자 로컬 PC에서 ProxyJump를 사용합니다.

⸻

Security Group

● 이유
Public ALB, NAT+Bastion, Kubernetes Worker, PostgreSQL 및 GPU AI
사이의 접근 경로를 최소 권한 원칙으로 제한합니다.
인터넷에는 Public ALB의 HTTPS와 관리자 IP용 SSH만 공개합니다.

● 사양
Public ALB Security Group 1개
NAT+Bastion Security Group 1개
Kubernetes Worker Security Group 1개
PostgreSQL Security Group 1개
GPU AI Security Group 1개

● 허용 정책
인터넷 → Public ALB: TCP 443
인터넷 → Public ALB: TCP 80은 HTTPS Redirect 용도로만 선택 허용
관리자 지정 IP → NAT+Bastion: TCP 22
Public ALB → ingress-nginx: Worker NodePort TCP 31664
  (ALB 서비스·헬스체크 IP 10.30.2.10, 10.30.2.27,
   10.30.2.229, 10.30.2.232에서만 허용)
NAT+Bastion → Worker Node, PostgreSQL, GPU AI: TCP 22
Backend Pod 또는 Worker Node → PgBouncer: TCP 6432
Alembic Job → PostgreSQL: TCP 5432
Backend Pod 또는 Worker Node → GPU AI FastAPI: TCP 80
Worker Node → Container Registry: NAT 경유 HTTPS
PostgreSQL VM → Object Storage: NAT 경유 HTTPS

● 외부 공개 금지
PostgreSQL: TCP 5432
PgBouncer: TCP 6432
llama-server: TCP 8081
Milvus: TCP 19530
MinIO: TCP 9000, 9001
Milvus 관리 포트: TCP 9091

GPU AI FastAPI를 제외한 GPU 내부 서비스 포트는 가능하면
127.0.0.1에 바인딩하고 GPU VM 내부에서만 사용합니다.

Cloud DNS

● 이유
서비스 도메인을 Public ALB와 연결하고, VM의 IP가 변경되더라도
DNS Record 변경으로 연결 대상을 관리합니다.
PostgreSQL 및 GPU AI VM도 사설 IP 하드코딩 대신 내부 이름을
사용하는 것을 권장합니다.

● 사양
Public DNS Zone 1개
서비스 도메인 1개
Public ALB Alias 또는 CNAME 연결
Private DNS Zone은 사용 가능 여부 확인 후 적용 권장

● Public 라우팅 예시
service.example.com/     → Frontend Service
service.example.com/api  → Backend Service

● Private DNS 예시
db.internal → PostgreSQL VM Private IP
ai.internal → GPU AI VM Private IP

별도 관리자 서비스가 확정되지 않았으므로 관리자 서브도메인은
현재 구성에 포함하지 않습니다.

⸻

SSL Certificate

● 이유
사용자 로그인 정보, JWT 및 API 요청을 HTTPS로 암호화합니다.
인증서는 Public ALB에 적용하여 Kubernetes Pod에서 인증서를
직접 관리하지 않도록 합니다.

● 사양
공인 SSL 인증서 1개
Public ALB HTTPS 443 Listener 연결
HTTP 80 → HTTPS 443 Redirect
TLS 1.2 이상 적용
인증서 갱신 방식 확인

인증서는 별도 생성한 Public ALB `LoadBalancer03`에 적용합니다.
ingress-nginx Service는 고정 NodePort 31664/31364를 사용하며,
Kubernetes `LoadBalancer` Service는 사용하지 않습니다.

Kubernetes Ingress

● 이유
Public ALB에서 전달된 요청을 Kubernetes 내부 Frontend와 Backend
Service로 라우팅합니다.

● 사양
ingress-nginx Controller Replica 2개
Frontend Service 연결
Backend Service 연결
Path 기반 라우팅
헬스체크 경로 설정
Public ALB에서 TLS 종료

● 라우팅
/     → Frontend Service
/api  → Backend Service

Frontend 및 Backend Deployment는 각각 최소 Replica 2개로 시작하고,
topologySpreadConstraints 또는 Pod anti-affinity를 적용해 서로 다른
Worker Node에 분산 배치합니다.

PostgreSQL + PgBouncer

● 이유
PostgreSQL은 상태 저장 워크로드이므로 Kubernetes 외부의 전용 VM에서
운영합니다.
Backend Pod 증가에 따른 PostgreSQL 연결 수 증가를 제어하기 위해
PgBouncer를 같은 VM에 설치합니다.

● 사양
PostgreSQL VM 1대
Public IP 미할당
PostgreSQL 데이터용 별도 Block Storage
PgBouncer TCP 6432
PostgreSQL TCP 5432
PgBouncer pool_mode=transaction
Backend Pod당 Uvicorn Worker 1개
Backend 최소 Replica 2, 초기 최대 Replica 4

● 연결
Backend Deployment DATABASE_URL
postgresql+psycopg://USER:PASSWORD@db.internal:6432/cineverse

Alembic Job DATABASE_URL
postgresql+psycopg://USER:PASSWORD@db.internal:5432/cineverse

● 애플리케이션 연결 설정
SQLAlchemy NullPool 적용
psycopg prepare_threshold=None 적용
운영 SQL echo 비활성화

PgBouncer의 max_client_conn, default_pool_size와 PostgreSQL의
max_connections는 DB VM 사양과 실제 부하 측정 후 확정합니다.

GPU AI Server

● 이유
기존 CUDA, llama.cpp, Python 가상환경 및 Milvus 구성을 유지하기 위해
Kubernetes 외부의 전용 GPU VM에서 운영합니다.

● 사양
GPU VM 1대
Private Subnet 배치
Public IP 미할당
기존 서버 커스텀 이미지 기반 생성
AI FastAPI
llama-server
Milvus
etcd
MinIO

● 통신
Backend Pod → AI FastAPI: TCP 80
AI FastAPI → llama-server: localhost TCP 8081
AI FastAPI → Milvus: localhost TCP 19530
Milvus → etcd 및 MinIO: GPU VM 내부 통신

GPU AI VM과 PostgreSQL VM의 자동 복구 및 이중화는 현재 범위에서
제외하고, 복구 계획을 문서화한 후 향후 단계에서 추가합니다.

⸻

Object Storage

● 이유
PostgreSQL 백업과 사용자 프로필 이미지를 VM 및 Pod 로컬 디스크와
분리해 저장합니다.
Pod 재시작, Worker Node 교체 또는 VM 장애가 발생해도 중요 데이터를
유지할 수 있도록 합니다.

● 사용 범위
PostgreSQL pg_dump 백업 저장
사용자 프로필 이미지 원본 또는 서비스용 이미지 저장
필요 시 운영 로그 장기 보관

● PostgreSQL 백업
백업 전용 Private Bucket 1개
Public Access 차단
서비스 계정 기반 S3 Access Key 사용
DB 추가 백업 주기 1일
일간, 주간, 월간 보존 정책 수립
백업 데이터 암호화
백업 성공 여부 검증
월 1회 복구 테스트 권장
PostgreSQL VM에서 NAT를 경유해 HTTPS로 업로드

● 프로필 이미지
현재 Backend Pod의 /app/app/profile_images 로컬 저장 방식을
Object Storage 업로드 방식으로 변경
DB에는 로컬 파일 경로 대신 Object Key 또는 서비스 URL 저장
Backend Pod가 직접 로컬 파일을 제공하지 않도록 변경
Bucket Public Access 정책은 서비스 요구사항에 맞게 결정
가능하면 비공개 Bucket과 제한된 접근 URL 사용

● 제외 대상
Kubernetes Manifest는 Git Repository에서 버전 관리
비밀번호, JWT Secret, S3 Secret Key 등 민감정보는 백업 파일에
평문으로 저장하지 않음

Monitoring

● 이유
Kubernetes Node, Pod, PostgreSQL, PgBouncer, GPU 및 애플리케이션
상태를 통합 모니터링하여 장애를 조기에 감지합니다.

● 사양
Kubernetes 클러스터 1개 모니터링
Worker Node 2대 모니터링
GPU Server 1대 모니터링
PostgreSQL 및 PgBouncer 모니터링
CPU, RAM, Disk, Network 수집
Pod 상태 및 재시작 횟수 수집
API 응답시간 및 오류율 수집
PostgreSQL 연결 수 및 저장공간 수집
PgBouncer Client 및 Server 연결 수 수집
GPU 온도, 전력, 사용률 및 VRAM 수집
GPU Xid, ECC 및 CUDA OOM 오류 감시
Milvus, etcd, MinIO 상태 감시
알림 채널 이메일 또는 메신저 연동

● 초기 알림 기준
CPU 및 RAM 지속 고사용률
Disk 사용률 80% 이상
API 오류율 임계치 초과
Pod 재시작 반복
PostgreSQL 또는 PgBouncer 연결 실패
GPU Xid, ECC 또는 CUDA OOM 발생
ALB 헬스체크 실패

GPU 모델은 정상 상태에서도 VRAM을 많이 선점하므로 VRAM 사용률
단독으로 장애를 판단하지 않고 OOM, 오류 및 비정상 증가와 함께 봅니다.
정확한 임계치는 실제 운영 데이터 수집 후 조정합니다.

Centralized Logging

● 이유
Pod가 재시작되거나 Worker Node가 교체돼도 애플리케이션 로그와
오류 기록을 유지할 수 있도록 중앙 저장소로 수집합니다.

● 적용 범위
Frontend 및 ingress-nginx 로그
Backend API 로그
GPU AI 추론 서버 로그
PostgreSQL 및 PgBouncer 오류 로그
NAT+Bastion 관리 접근 로그
개인정보, JWT, Password 및 API Key 마스킹

Frontend와 Backend는 로그를 컨테이너 표준 출력으로 기록합니다.
구체적인 로그 수집 도구와 보관 기간은 비용과 운영 요구사항을
확인한 후 확정합니다.

Container Vulnerability Scanning — 권장

● 이유
Kubernetes에 배포하는 Frontend와 Backend 컨테이너 이미지의
운영체제 패키지 및 라이브러리 취약점을 배포 전에 탐지합니다.

● 사양
Frontend Private Repository 1개
Backend Private Repository 1개
GitHub Actions에서 이미지 Build 후 취약점 검사
검사 통과 후 Container Registry Push
Critical 및 High 취약점 확인
사용하지 않는 구버전 이미지 정리

초기에는 GitHub Actions에서 Trivy 등의 도구를 사용할 수 있습니다.
Critical 취약점의 자동 배포 차단 정책은 오탐 및 예외 처리 기준을
정한 후 적용합니다.

CI/CD

● 현재 단계
GitHub Actions에서 테스트 수행
Frontend 및 Backend 컨테이너 이미지 Build
취약점 검사

현재 단계의 단일 장애점 및 향후 과제

Private Subnet 1개를 사용하므로 가용 영역 전체 장애에는 대응하지 못합니다.
NAT+Bastion VM 장애 시 인터넷 아웃바운드와 관리 접속이 중단됩니다.
PostgreSQL VM 장애 시 데이터베이스 기능이 중단됩니다.
GPU AI VM 장애 시 AI 기능이 중단됩니다.

현재 단계에서는 위 단일 장애점을 수용하고 다음 항목을 복구 계획으로
문서화한 뒤 향후 확장 단계에서 구현합니다.

PostgreSQL Standby 및 자동 Failover
두 번째 GPU AI Server
NAT와 Bastion 역할 분리
다중 가용영역 및 추가 Subnet
Private Self-hosted Runner 또는 GitOps CD
중앙 로그 수집 도구 확정
